This summarizes every verification activity performed against `model/uav_altitude_hold.slx` and its generated code, what tool produced each result, and where the underlying evidence lives.

## Requirements traceability

`requirements/uav_altitude_hold_requirements.slreqx` (Requirements Toolbox), generated by `scripts/generate_requirements.m`:

- 7 High-Level Requirements (HLR-1 … HLR-7): control law, proportional feedback, rate damping, bounded-integral action, input validity gating, hover fallback, output saturation / fixed-rate execution.
- 13 Low-Level Requirements (LLR-1 … LLR-13): implementation-level decomposition of each HLR (gain values, range bounds, clamp limits, fallback value).
- 26 traceability links: 13 HLR→LLR links, 13 LLR→model-block links (via `slreq.createLink`).

## Model-level tests

`tests/test_uav_altitude_hold.m` (`matlab.unittest`, run via `mcp__matlab__run_matlab_test_file` or `runtests`):

- **14/14 passed.**
- Covers: positive/negative tracking error, zero-error trim hold, rate damping, saturation at both limits, and all 7 fallback paths (sensor invalid; alt_cmd/alt_meas/vz_meas each below and above their valid range; non-finite input).

## Simulink Test harness / baseline tests

`tests/uav_altitude_hold_harness_tests.mldatx` (Simulink Test Manager), generated by `scripts/generate_test_harnesses.m` + `scripts/generate_harness_tests.m`:

- Two harnesses, each with a Test Sequence block driving a scripted scenario:
  - `model/uav_altitude_hold_Harness1.slx` (5 steps) — nominal closed-loop tracking (hover → climb → descend) plus both output-saturation boundaries (high and low).
  - `model/uav_altitude_hold_Harness2.slx` (9 steps) — input-validity edge cases: valid baseline, sensor invalid, then each of the 6 validity-gate range checks (`alt_cmd`, `alt_meas`, `vz_meas` — both below and above their valid range) individually violated, then recovery to valid.
- Both wired to baseline test cases (`tests/baseline_harness1.mat`, `tests/baseline_harness2.mat`) captured from current model behavior.
- **2/2 passed.**
- Steps were deliberately chosen so the two harnesses, run on their own (without the MATLAB unit tests below), individually exercise every validity-gate condition and both saturation limits — not just the aggregate valid/invalid outcome.

- **Decision: 100%, Condition: 100%, MC/DC: 100%, Execution: 100%** — at every level of the model hierarchy (root, Input Validity Gate, Control Law).

## Polyspace Code Prover

Run via the classic `polyspace-code-prover` CLI (`polyspace/run_code_prover.sh`), with input ranges bounded to a physically realistic sensor domain (`polyspace/drs.xml`):

- **Green: 29, Orange: 0, Red: 0 (100% proven).**
- Without the input-range bound, 2 Overflow checks report Orange (Code Prover correctly can't rule out float overflow for the full unconstrained `double` range); bounding `alt_cmd`/`alt_meas`/`vz_meas` to `[-10000, 10000]` — generous relative to the validity gate's `[0,500]`/`[-15,15]` — resolves both.

## PSTUnit C unit tests

`tests/c/test_uav_altitude_hold.c`, built and run per `tests/c/build_and_run.sh` (PSTUnit against the generated `uav_altitude_hold_step()`), results at `evidence/pstunit/results.txt`:

- **14/14 passed.**
- Single-call-per-test design: each test resets model state (`uav_altitude_hold_initialize()`) then calls `uav_altitude_hold_step()` once, so expected `throttle_cmd` values are the exact single-step analytic results (no integrator settling), mirroring the same 14 scenarios as the MATLAB unit tests.
